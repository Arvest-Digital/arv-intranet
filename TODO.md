## Staged migrations from `generate-data-model` don't fit the drizzle workflow

The SDLC skill `generate-data-model` wrote hand-written, timestamp-named `.up.sql` / `.down.sql` pairs to
`docs/features/resource-scheduling/migrations/` (2026-10-30). This repo only uses migrations generated by
drizzle-kit from `modules/*/src/infrastructure/schema.ts`: sequential `NNNN_*.sql` files plus a journal and
snapshots, with no down migrations (`.claude/rules/backend/db.md`). Copied into `packages/migrations/drizzle/` as is,
these files would be invisible to `drizzle-kit migrate` / `pnpm db:status`, and the next `pnpm db:generate` would
recreate the tables.

Current workaround (in `docs/features/resource-scheduling/data-model.md`): the staged `.up.sql` is a spec.
`implement-tasks` writes `schema.ts`, runs `pnpm db:generate` and diffs the result against it. The `.down.sql`
files are not promoted.

To decide:
- Keep the staged SQL as a spec, or have the skill emit `schema.ts` drafts instead of SQL for this repo?
- Drop `.down.sql`, or keep it as documentation of a manual rollback?
- Teach the SDLC plugin (`generate-data-model`, `implement-tasks`) to detect drizzle-kit and follow it, instead of
  the course defaults (timestamp names, `IF NOT EXISTS`, `CONCURRENTLY`, bootstrapping `rules/migrations.md`).
